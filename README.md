# Translation & Error Handling System — Agriculture & Gardens Management System

This document explains how bilingual (EN/AR) UI text is stored, resolved, kept in
sync with APEX, and surfaced to users through the central error handler — all
built around a single package: **`APP_TRANSLATE_PKG`**.

---

## 1. Purpose

Every user-facing string in the AGR applications — labels, buttons, error
messages, constraint violations — is stored once in `APP_UTIL_TRANSLATE` and
resolved at runtime in the user's language. The system has three moving parts
that work together:

| Part | Responsibility |
|---|---|
| **Translation store** | `APP_UTIL_TRANSLATE` table + `APP_TRANSLATE_PKG` — the single source of truth for bilingual text |
| **APEX sync** | `TRG_TRANSLATE_APEX_SYNC` — pushes rows into APEX's own translation store so `apex_lang.message()` and page-level translations pick up the same text |
| **Error handler** | `APP_TRANSLATE_PKG.AGR_ERROR_HANDLER` — the APEX application Error Handling Function; converts raw Oracle errors into friendly bilingual messages, auto-seeding new ones the first time they occur |

---

## 2. Database Objects

| Object | Type | Purpose |
|---|---|---|
| `APP_UTIL_TRANSLATE` | Table | Stores every translated string, keyed by `(CODE, LANG)` |
| `APP_UTIL_TRANSLATE_BIU` | Trigger (row, before) | Maintains `ROW_VERSION`, `CREATED_ON/BY`, `UPDATED_ON/BY` automatically |
| `TRG_TRANSLATE_APEX_SYNC` | Trigger (compound) | Syncs changed rows to APEX's built-in translation store after each INSERT/UPDATE statement |
| `TRG_SEED_CONSTRAINT_MSG` | Trigger (DDL, schema-level) | Auto-seeds a placeholder translation the moment a new constraint is created on any `AGR_%` table |
| `APP_TRANSLATE_PKG` | Package | All translation logic, APEX sync, constraint-message seeding, and the application error handler |
| `VW_AGR_CONSTRAINT_MESSAGES` | View | Combines Oracle's constraint dictionary with `APP_UTIL_TRANSLATE` to show translation status per constraint — the source for the admin page |

## 3. Table: `APP_UTIL_TRANSLATE`

```sql
CREATE TABLE "APP_UTIL_TRANSLATE"
(  "ID"            NUMBER GENERATED BY DEFAULT ON NULL AS IDENTITY NOT NULL ENABLE,
   "CODE"          VARCHAR2(300) NOT NULL ENABLE,
   "APP_ID"        NUMBER,
   "PAGE_ID"       NUMBER,
   "LANG"          VARCHAR2(10)  NOT NULL ENABLE,
   "TEXT_MESSAGE"  VARCHAR2(4000) NOT NULL ENABLE,
   "DESCRIPTION"   VARCHAR2(1000),
   "IS_USED_IN_JS" VARCHAR2(1) DEFAULT 'N',
   "IS_ACTIVE"     VARCHAR2(1) DEFAULT 'Y',
   "CREATED_ON"    TIMESTAMP(6),
   "CREATED_BY"    VARCHAR2(255),
   "UPDATED_ON"    TIMESTAMP(6),
   "UPDATED_BY"    VARCHAR2(255),
   "ROW_VERSION"   NUMBER NOT NULL ENABLE,
   "IS_SYNC"       VARCHAR2(1) DEFAULT 'N',
    CHECK (is_used_in_js IN ('Y','N')) ENABLE,
    CHECK (is_active     IN ('Y','N')) ENABLE,
    PRIMARY KEY ("ID") ENABLE,
    CONSTRAINT "UQ_TRANSLATE_KEY" UNIQUE ("CODE", "LANG") ENABLE
);

CREATE INDEX "IDX_TRANS_APP" ON "APP_UTIL_TRANSLATE" ("APP_ID", "PAGE_ID", "LANG");
CREATE INDEX "IDX_TRANS_JS"  ON "APP_UTIL_TRANSLATE" ("IS_USED_IN_JS", "LANG");
```

> **⚠️ Design note — `UQ_TRANSLATE_KEY` is `(CODE, LANG)` only.**
> `APP_ID` and `PAGE_ID` are *not* part of the unique key. This means only
> **one** row can ever exist for a given `CODE` + `LANG` combination across
> the whole system — you cannot currently have two different app-scoped
> overrides of the same code. `GET_TRANSLATE_MESSAGE`'s app/page-scoped
> lookup tiers exist in the code but in practice will only ever find the one
> row that exists. If per-app overrides are needed later, `UQ_TRANSLATE_KEY`
> must be widened to `(CODE, APP_ID, PAGE_ID, LANG)`.

### Column reference

| Column | Meaning |
|---|---|
| `CODE` | Message key, e.g. `LBL_REQUEST_NO`, `MSG_SUBMIT_SUCCESS`, `BTN_APPROVE`. Convention: `LBL_`=label, `MSG_`=message, `BTN_`=button, `TIT_`=page title, `ERR_`=error |
| `APP_ID` | APEX app scope. `NULL` = shared across all apps |
| `LANG` | `EN` or `AR` |
| `TEXT_MESSAGE` | The translated text. May contain `#SUBSTITUTION#` syntax or `%0`–`%7` placeholder tokens (see `FORMAT_MESSAGE`) |
| `IS_USED_IN_JS` | `Y` = must be included when syncing to APEX so it's available client-side |
| `IS_SYNC` | `Y` once `SYNC_TO_APEX` has successfully pushed this row to APEX. Set automatically — never set manually |
| `ROW_VERSION` | Optimistic-lock counter, maintained entirely by `APP_UTIL_TRANSLATE_BIU` |

### `APP_UTIL_TRANSLATE_BIU` — audit trigger

```sql
CREATE OR REPLACE TRIGGER "APP_UTIL_TRANSLATE_BIU"
  BEFORE INSERT OR UPDATE ON APP_UTIL_TRANSLATE
  FOR EACH ROW
BEGIN
  IF INSERTING THEN
    :NEW.ROW_VERSION := 1;
  ELSIF UPDATING THEN
    :NEW.ROW_VERSION := NVL(:OLD.ROW_VERSION, 0) + 1;
  END IF;
  IF INSERTING THEN
    :NEW.CREATED_ON := SYSDATE;
    :NEW.CREATED_BY := COALESCE(SYS_CONTEXT('APEX$SESSION','APP_USER'), USER);
  END IF;
  :NEW.UPDATED_ON := SYSDATE;
  :NEW.UPDATED_BY := COALESCE(SYS_CONTEXT('APEX$SESSION','APP_USER'), USER);
END;
```

Runs on **every** insert/update, including the ones fired internally by
`SYNC_TO_APEX`'s write-back (see §5).

## 4. Translation Flow

```
Application code / page process
        │
        ▼
APP_TRANSLATE_PKG.ADD_TRANSLATE_MESSAGE(code, lang, text, app_id, ...)
        │
        ├─► UPDATE APP_UTIL_TRANSLATE ... WHERE CODE=? AND LANG=? AND APP_ID=? AND PAGE_ID=?
        │       │
        │       └─► if SQL%ROWCOUNT = 0 → INSERT instead (upsert)
        │
        ├─► fires APP_UTIL_TRANSLATE_BIU (sets audit columns + ROW_VERSION)
        │
        ├─► fires TRG_TRANSLATE_APEX_SYNC (compound trigger, see §5)
        │       └─► queues the row; AFTER STATEMENT calls SYNC_TO_APEX
        │
        └─► ALSO calls SYNC_TO_APEX directly, best-effort
                (this means a row can be synced twice per statement —
                 see the note at the end of §5)

Runtime read:
APP_TRANSLATE_PKG.GET_TRANSLATE_MESSAGE(code, lang, app_id, page_id, default)
        │
        ├─► 1. exact match: CODE + LANG + APP_ID + PAGE_ID
        ├─► 2. CODE + LANG + APP_ID (page_id IS NULL)
        ├─► 3. CODE + LANG (APP_ID IS NULL, PAGE_ID IS NULL)  ← the only tier
        │       that will ever match in practice, given UQ_TRANSLATE_KEY
        ├─► 4. p_default_value if supplied
        └─► 5. bare p_code as last resort
```

### `ADD_TRANSLATE_MESSAGE` — write path

```sql
PROCEDURE add_translate_message (
    p_code IN VARCHAR2, p_lang IN VARCHAR2, p_text_message IN VARCHAR2,
    p_app_id IN NUMBER DEFAULT NULL, p_page_id IN NUMBER DEFAULT NULL,
    p_description IN VARCHAR2 DEFAULT NULL, p_is_used_in_js IN VARCHAR2 DEFAULT 'N'
) IS
BEGIN
  UPDATE app_util_translate
  SET text_message = p_text_message,
      description  = NVL(p_description, description),
      is_used_in_js = NVL(p_is_used_in_js, is_used_in_js),
      is_active     = 'Y'
  WHERE code = p_code AND lang = UPPER(p_lang)
    AND (app_id  = p_app_id  OR (app_id  IS NULL AND p_app_id  IS NULL))
    AND (page_id = p_page_id OR (page_id IS NULL AND p_page_id IS NULL));

  IF SQL%ROWCOUNT = 0 THEN
    INSERT INTO app_util_translate (code, app_id, page_id, lang, text_message,
                                     description, is_used_in_js, is_active)
    VALUES (p_code, p_app_id, p_page_id, UPPER(p_lang), p_text_message,
            p_description, NVL(p_is_used_in_js,'N'), 'Y');
  END IF;

  -- Keep APEX translation store in sync (best-effort — ignore APEX errors)
  BEGIN
    sync_to_apex(p_code, p_lang, p_app_id);
  EXCEPTION WHEN OTHERS THEN NULL;
  END;
END add_translate_message;
```

### `GET_TRANSLATE_MESSAGE` — read path

```sql
FUNCTION get_translate_message (
    p_code IN VARCHAR2, p_lang IN VARCHAR2 DEFAULT 'EN',
    p_app_id IN NUMBER DEFAULT NULL, p_page_id IN NUMBER DEFAULT NULL,
    p_default_value IN VARCHAR2 DEFAULT NULL
) RETURN VARCHAR2 IS
  v_text VARCHAR2(4000);
  v_lang VARCHAR2(10) := UPPER(NVL(p_lang,'EN'));
BEGIN
  IF p_app_id IS NOT NULL AND p_page_id IS NOT NULL THEN
    BEGIN
      SELECT text_message INTO v_text FROM app_util_translate
      WHERE code=p_code AND lang=v_lang AND app_id=p_app_id
        AND page_id=p_page_id AND is_active='Y';
      RETURN v_text;
    EXCEPTION WHEN no_data_found THEN NULL; END;
  END IF;

  IF p_app_id IS NOT NULL THEN
    BEGIN
      SELECT text_message INTO v_text FROM app_util_translate
      WHERE code=p_code AND lang=v_lang AND app_id=p_app_id
        AND page_id IS NULL AND is_active='Y';
      RETURN v_text;
    EXCEPTION WHEN no_data_found THEN NULL; END;
  END IF;

  BEGIN
    SELECT text_message INTO v_text FROM app_util_translate
    WHERE code=p_code AND lang=v_lang
      AND app_id IS NULL AND page_id IS NULL AND is_active='Y';
    RETURN v_text;
  EXCEPTION WHEN no_data_found THEN NULL; END;

  IF p_default_value IS NOT NULL THEN RETURN p_default_value; END IF;
  RETURN p_code;  -- last resort
END get_translate_message;
```

### `FORMAT_MESSAGE` / `GET_FORMAT_MESSAGE` — parameterised messages

Placeholder tokens are **`%0` through `%7`**, not `{NAME}` style tokens:

```sql
v_msg := app_translate_pkg.get_format_message(
             p_code   => 'MSG_QTY_EXCEEDS_LIMIT',
             p_lang   => 'EN',
             p_param1 => TO_CHAR(v_qty),
             p_param2 => TO_CHAR(v_limit)
         );
-- Stored text: 'You requested %0 units but the limit is %1.'
-- Result:      'You requested 45 units but the limit is 30.'
```

> **⚠️ Known bug in `FORMAT_MESSAGE`**: the branches for `p_param6`,
> `p_param7`, `p_param8` all call `REPLACE(v_result, '%5'/'%6'/'%7', p_param5)`
> — they reuse `p_param5` instead of `p_param6`/`p_param7`/`p_param8`
> respectively. Only the first 5 parameters (`%0`–`%4`) currently work
> correctly. Fix by changing each `p_param5` reference in those three
> branches to match its own parameter.

## 5. APEX Sync — `TRG_TRANSLATE_APEX_SYNC`

A **compound trigger** — deliberately not a simple row trigger, because
`SYNC_TO_APEX` needs to query `APP_UTIL_TRANSLATE` itself, which would raise
`ORA-04091: table is mutating` from an ordinary `AFTER ... FOR EACH ROW`
trigger. Splitting the work across two trigger timings avoids this
structurally rather than by working around it:

```sql
CREATE OR REPLACE TRIGGER TRG_TRANSLATE_APEX_SYNC
  FOR INSERT OR UPDATE ON APP_UTIL_TRANSLATE
  COMPOUND TRIGGER

  TYPE T_SYNC_ROW  IS RECORD (CODE APP_UTIL_TRANSLATE.CODE%TYPE,
                              LANG APP_UTIL_TRANSLATE.LANG%TYPE,
                              APP_ID APP_UTIL_TRANSLATE.APP_ID%TYPE);
  TYPE T_SYNC_LIST IS TABLE OF T_SYNC_ROW INDEX BY PLS_INTEGER;
  G_ROWS T_SYNC_LIST;
  G_IDX  PLS_INTEGER := 0;

  -- Collect only rows with a MEANINGFUL change — no table access here.
  AFTER EACH ROW IS
  BEGIN
    IF :NEW.IS_ACTIVE = 'Y'
       AND ( INSERTING
             OR NVL(:OLD.text_message,  CHR(0)) <> NVL(:NEW.text_message,  CHR(0))
             OR NVL(:OLD.is_used_in_js, CHR(0)) <> NVL(:NEW.is_used_in_js, CHR(0))
             OR NVL(:OLD.code,          CHR(0)) <> NVL(:NEW.code,          CHR(0))
             OR NVL(:OLD.lang,          CHR(0)) <> NVL(:NEW.lang,          CHR(0))
             OR NVL(:OLD.app_id, -1)            <> NVL(:NEW.app_id, -1)
             OR NVL(:OLD.is_active,     CHR(0)) <> NVL(:NEW.is_active,     CHR(0)) )
    THEN
      G_IDX := G_IDX + 1;
      G_ROWS(G_IDX).CODE := :NEW.CODE; G_ROWS(G_IDX).LANG := :NEW.LANG;
      G_ROWS(G_IDX).APP_ID := :NEW.APP_ID;
    END IF;
  END AFTER EACH ROW;

  -- Statement is complete — table is no longer mutating. Safe to query it.
  AFTER STATEMENT IS
  BEGIN
    FOR I IN 1 .. G_IDX LOOP
      BEGIN
        APP_TRANSLATE_PKG.SYNC_TO_APEX(G_ROWS(I).CODE, G_ROWS(I).LANG, G_ROWS(I).APP_ID);
      EXCEPTION WHEN OTHERS THEN
        APP_UTIL_PKG.ADD_DEBUG(p_log_msg => 'sync failed for ' || G_ROWS(I).CODE,
                                p_log_type => APP_UTIL_PKG.C_LOG_WARN, ...);
      END;
    END LOOP;
    G_ROWS.DELETE; G_IDX := 0;
  END AFTER STATEMENT;
END TRG_TRANSLATE_APEX_SYNC;
```

**Why the change-detection filter matters**: without it, every `UPDATE` —
even one that only touches `UPDATED_ON`/`UPDATED_BY` via the BIU trigger —
would queue a redundant APEX sync. The filter only queues a row when
`TEXT_MESSAGE`, `IS_USED_IN_JS`, `CODE`, `LANG`, `APP_ID`, or `IS_ACTIVE`
actually changed value.

### `SYNC_TO_APEX` — pushing one row into APEX

```sql
PROCEDURE sync_to_apex (p_code IN VARCHAR2, p_lang IN VARCHAR2, p_app_id IN NUMBER DEFAULT NULL) IS
  v_app_id NUMBER := p_app_id;   -- no session-context fallback — must be passed explicitly
BEGIN
  IF v_app_id IS NULL THEN RETURN; END IF;   -- guard: nothing to sync to without an app

  SELECT text_message, is_used_in_js INTO v_text, v_used_in_js
  FROM app_util_translate
  WHERE code=p_code AND lang=v_lang_upper AND is_active='Y' AND app_id=v_app_id
  FETCH FIRST 1 ROWS ONLY;
  -- ↑ NOTE: no longer falls back to a shared (APP_ID IS NULL) row.
  --   Global/shared translations are never pushed to APEX by this
  --   procedure — only rows that already have an explicit APP_ID.

  SELECT translation_entry_id INTO v_entry_id
  FROM apex_application_translations
  WHERE application_id=v_app_id AND translatable_message=p_code AND language_code=v_lang_lower;
  -- NO_DATA_FOUND → v_entry_id := NULL (will CREATE instead of UPDATE)

  apex_util.set_workspace(p_workspace => 'AGRICULTURE');  -- sets workspace context

  IF v_entry_id IS NOT NULL THEN
    apex_lang.update_message(p_id => v_entry_id, p_message_text => v_text);
  ELSE
    apex_lang.create_message(p_application_id => v_app_id, p_name => p_code,
                              p_language => v_lang_lower, p_message_text => v_text,
                              p_used_in_javascript => CASE WHEN v_used_in_js='Y' THEN TRUE ELSE FALSE END);
  END IF;

  -- Mark as synced (also backfills APP_ID if it was NULL)
  UPDATE app_util_translate SET is_sync='Y', app_id=NVL(app_id,p_app_id)
  WHERE code=p_code AND lang=UPPER(p_lang) AND app_id=p_app_id;
END sync_to_apex;
```

> **Note on the write-back UPDATE**: this final `UPDATE` fires
> `TRG_TRANSLATE_APEX_SYNC` again as a fresh statement (not a recursive call
> within the same trigger firing — the original statement has already
> completed by the time `AFTER STATEMENT` runs `SYNC_TO_APEX`). The
> change-detection filter in `AFTER EACH ROW` normally evaluates to `FALSE`
> on this second pass (only `IS_SYNC`/`APP_ID` changed, and `APP_ID` only
> changes once, from `NULL` to a real value) — so this is self-terminating
> and does not loop.

> **Consequence of `SYNC_TO_APEX` requiring an explicit `APP_ID`**: any row
> inserted with `p_app_id => NULL` (the shared/global scope) is **never**
> synced to APEX, by design of the current guard clause. If a shared string
> needs to appear via `apex_lang.message()` in a specific app, either call
> `ADD_TRANSLATE_MESSAGE` with that app's `APP_ID` explicitly, or call
> `SYNC_ALL_TO_APEX(p_app_id => <id>)` — note that its own row source also
> requires `APP_ID` to be populated (see §6).

### `SYNC_ALL_TO_APEX` — bulk re-sync

```sql
PROCEDURE sync_all_to_apex (p_app_id IN NUMBER DEFAULT NULL, p_lang IN VARCHAR2 DEFAULT NULL) IS
BEGIN
  FOR r IN (
    SELECT code, lang, app_id FROM app_util_translate
    WHERE is_active='Y'
      AND (p_app_id IS NULL OR app_id=p_app_id OR app_id IS NULL)
      AND (p_lang   IS NULL OR lang=UPPER(p_lang))
    ORDER BY app_id NULLS LAST, code, lang
  ) LOOP
    BEGIN
      sync_to_apex(r.code, r.lang, NVL(r.app_id, p_app_id));
      v_synced := v_synced + 1;
    EXCEPTION WHEN OTHERS THEN v_failed := v_failed + 1;
    END;
  END LOOP;
  app_util_pkg.add_debug(p_log_msg => 'SYNC_ALL_TO_APEX completed. Synced='
      || v_synced || ' Failed=' || v_failed, ...);
END sync_all_to_apex;
```

Use after a bulk data migration or initial environment seeding — pass
`p_app_id` to re-sync everything relevant to one application.

## 6. Constraint Message Auto-Seeding

Two independent mechanisms feed friendly bilingual text for Oracle
constraint violations into `APP_UTIL_TRANSLATE`, so the error handler (§7)
never has to show a raw `ORA-00001` to a user.

### 6a. `TRG_SEED_CONSTRAINT_MSG` — automatic, at DDL time

Fires the moment a developer creates or alters a table:

```sql
CREATE OR REPLACE TRIGGER TRG_SEED_CONSTRAINT_MSG
    AFTER CREATE OR ALTER ON SCHEMA
DECLARE
    PRAGMA AUTONOMOUS_TRANSACTION;
    V_OBJ_TYPE VARCHAR2(30)  := ORA_DICT_OBJ_TYPE;
    V_OBJ_NAME VARCHAR2(128) := ORA_DICT_OBJ_NAME;
BEGIN
    IF V_OBJ_TYPE NOT IN ('TABLE') THEN RETURN; END IF;
    IF V_OBJ_NAME NOT LIKE 'AGR_%' THEN RETURN; END IF;

    FOR C IN (
        SELECT CONSTRAINT_NAME, CONSTRAINT_TYPE
        FROM   USER_CONSTRAINTS
        WHERE  TABLE_NAME = V_OBJ_NAME
        AND    CONSTRAINT_TYPE IN ('U','R','C')
        AND    CONSTRAINT_NAME NOT LIKE 'SYS_%'
        AND    CONSTRAINT_NAME NOT LIKE 'BIN$%'
        AND NOT EXISTS (SELECT 1 FROM APP_UTIL_TRANSLATE T
                         WHERE T.CODE = CONSTRAINT_NAME AND T.LANG = 'EN')
    ) LOOP
        -- direct INSERT (not the package) — DDL triggers must not call
        -- packages that could themselves trigger further DDL or a commit
        -- conflict; this is by design.
        INSERT INTO APP_UTIL_TRANSLATE (CODE, LANG, TEXT_MESSAGE, DESCRIPTION,
            APP_ID, PAGE_ID, IS_USED_IN_JS, IS_ACTIVE, CREATED_ON, CREATED_BY)
        VALUES (C.CONSTRAINT_NAME, 'EN', '[UNTRANSLATED] Constraint: '||C.CONSTRAINT_NAME,
            ..., NULL, NULL, 'N', 'Y', SYSTIMESTAMP, 'TRG_SEED_CONSTRAINT_MSG');
        -- (and again for 'AR' with '[غير مترجم] قيد: ' prefix)
    END LOOP;
    COMMIT;
EXCEPTION WHEN OTHERS THEN ROLLBACK;  -- must never block the DDL statement
END;
```

Runs in its own autonomous transaction and swallows all errors — a schema
migration is never blocked by a translation-seeding failure.

### 6b. `PRC_SEED_CONSTRAINT_MESSAGES` — manual / bulk, on demand

```sql
PROCEDURE PRC_SEED_CONSTRAINT_MESSAGES (
    P_TABLE_PREFIX  IN VARCHAR2 DEFAULT 'AGR_%',
    P_APP_ID        IN NUMBER   DEFAULT NULL,
    P_OVERWRITE     IN VARCHAR2 DEFAULT 'N',   -- Y = refresh unfilled placeholders
    P_SEEDED_COUNT  OUT NUMBER,
    P_SKIPPED_COUNT OUT NUMBER
);
```

Scans **all** existing constraints matching the table prefix (not just newly
created ones), so it's the right tool to run once after restoring a schema
from an export, or to catch anything the DDL trigger might have missed
before it existed. `P_OVERWRITE => 'Y'` only touches rows whose text still
starts with the `[...]` placeholder pattern — it never overwrites a message
a translator has already filled in.

```sql
-- Example: bulk-seed everything, safe to run repeatedly
DECLARE
  v_seeded NUMBER; v_skipped NUMBER;
BEGIN
  APP_TRANSLATE_PKG.PRC_SEED_CONSTRAINT_MESSAGES(
      P_TABLE_PREFIX => 'AGR_%', P_OVERWRITE => 'N',
      P_SEEDED_COUNT => v_seeded, P_SKIPPED_COUNT => v_skipped);
  DBMS_OUTPUT.PUT_LINE(v_seeded || ' seeded, ' || v_skipped || ' already existed.');
END;
/
```

### 6c. Monitoring — `VW_AGR_CONSTRAINT_MESSAGES`

```sql
SELECT CONSTRAINT_NAME, TABLE_NAME, CONSTRAINT_TYPE_LABEL,
       COLUMN_NAMES, EN_MESSAGE, AR_MESSAGE, TRANSLATION_STATUS
FROM   VW_AGR_CONSTRAINT_MESSAGES
WHERE  TRANSLATION_STATUS IN ('MISSING','PENDING')
ORDER  BY TABLE_NAME;
```

`TRANSLATION_STATUS` values:

| Status | Meaning |
|---|---|
| `MISSING` | No `APP_UTIL_TRANSLATE` row at all for this constraint |
| `PENDING` | A row exists but still has the `[UNTRANSLATED]` / `[غير مترجم]` placeholder |
| `PARTIAL` | One language filled in, the other missing |
| `TRANSLATED` | Both EN and AR have real translator-provided text |

This is the recommended source for an admin page where a translator reviews
and fills in the friendly message for each newly-created constraint.

## 7. Error Handler — `APP_TRANSLATE_PKG.AGR_ERROR_HANDLER`

Registered as the **Error Handling Function** on every AGR application
(Shared Components → Application Properties → Error Handling). Converts raw
Oracle errors into friendly, bilingual, field-highlighted messages.

### 7a. Language detection

```sql
FUNCTION F_GET_LANG RETURN VARCHAR2 IS
  V_PREF VARCHAR2(100);
BEGIN
  V_PREF := V('G_LANG');   -- custom application item, NOT FSP_LANGUAGE_PREFERENCE
  IF LOWER(V_PREF) LIKE 'ar%' THEN RETURN 'AR'; ELSE RETURN 'EN'; END IF;
EXCEPTION WHEN OTHERS THEN RETURN 'EN';
END;
```

Reads the custom **`G_LANG`** application item (set elsewhere in the app's
session/authentication logic) — not APEX's built-in `FSP_LANGUAGE_PREFERENCE`.

### 7b. Four cases handled

```
AGR_ERROR_HANDLER(p_error)
    │
    ├─ CASE 1: p_error.is_internal_error AND NOT is_common_runtime_error
    │     → log full detail via ADD_DEBUG + apex_debug.error(...) (9 diagnostic lines)
    │     → show generic bilingual message (code ERR_INTERNAL_APEX)
    │     → strip additional_info entirely (never expose SQL to the user)
    │
    ├─ CASE 2A: ora_sqlcode IN (-1, -2091, -2290, -2291, -2292)   [constraint violation]
    │     → EXTRACT_CONSTRAINT_NAME(p_error)
    │     → F_CONSTRAINT_MSG(constraint_name, lang)     [see 7c]
    │     → dynamically resolve & highlight the offending field   [see 7d]
    │
    ├─ CASE 2B: ora_sqlcode IS NOT NULL AND message still = raw ora text
    │     → GET_FIRST_ORA_ERROR_TEXT(p_error)    [strips the full ORA stack]
    │
    └─ CASE 2C: no page_item_name/column_alias set yet
          → APEX_ERROR.AUTO_SET_ASSOCIATED_ITEM as a fallback
          → upgrade display_location to C_INLINE_WITH_FIELD_AND_NOTIF if found
```

### 7c. `F_CONSTRAINT_MSG` — resolve or auto-seed

```sql
FUNCTION F_CONSTRAINT_MSG (P_CONSTRAINT_NAME IN VARCHAR2, P_LANG IN VARCHAR2) RETURN VARCHAR2 IS
    PRAGMA AUTONOMOUS_TRANSACTION;
BEGIN
    V_MSG_EN := APP_TRANSLATE_PKG.GET_TRANSLATE_MESSAGE(P_CODE => P_CONSTRAINT_NAME, P_LANG => 'EN');
    V_MSG_AR := APP_TRANSLATE_PKG.GET_TRANSLATE_MESSAGE(P_CODE => P_CONSTRAINT_NAME, P_LANG => 'AR');

    -- Auto-seed if genuinely missing OR GET_TRANSLATE_MESSAGE fell through
    -- to returning the bare code (its documented "last resort" behaviour)
    IF V_MSG_EN IS NULL AND V_MSG_AR IS NULL
       OR (V_MSG_EN = P_CONSTRAINT_NAME OR V_MSG_AR = P_CONSTRAINT_NAME) THEN
        ADD_TRANSLATE_MESSAGE(P_CODE => P_CONSTRAINT_NAME, P_LANG => 'EN',
            P_TEXT_MESSAGE => '[UNTRANSLATED] Constraint: '||P_CONSTRAINT_NAME, ...);
        ADD_TRANSLATE_MESSAGE(P_CODE => P_CONSTRAINT_NAME, P_LANG => 'AR',
            P_TEXT_MESSAGE => '[غير مترجم] قيد: '||P_CONSTRAINT_NAME, ...);
        ADD_DEBUG(...);  -- flags the developer/translator
        COMMIT;
        RETURN generic bilingual fallback;  -- "A data validation error occurred..."
    END IF;

    COMMIT;
    RETURN NVL(requested-language message, fallback);
EXCEPTION WHEN OTHERS THEN ROLLBACK; RETURN generic system-error message;
END F_CONSTRAINT_MSG;
```

Note this call to `GET_TRANSLATE_MESSAGE` does **not** pass `P_APP_ID` — it
always resolves at the shared/global tier, consistent with how
`TRG_SEED_CONSTRAINT_MSG` and `PRC_SEED_CONSTRAINT_MESSAGES` both seed with
`APP_ID = NULL`.

### 7d. Dynamic field highlighting — zero hardcoding

```sql
-- Step 1: resolve the DB column the constraint actually covers
SELECT COLUMN_NAME INTO V_COLUMN_NAME FROM USER_CONS_COLUMNS
WHERE CONSTRAINT_NAME = L_CONSTRAINT_NAME ORDER BY POSITION FETCH FIRST 1 ROWS ONLY;

-- Step 2a: find a matching page item on the CURRENT page
SELECT ITEM_NAME INTO V_ITEM_NAME FROM APEX_APPLICATION_PAGE_ITEMS
WHERE APPLICATION_ID = V_APP_ID AND PAGE_ID = V_PAGE_ID
AND UPPER(ITEM_NAME) LIKE '%\_' || UPPER(V_COLUMN_NAME) ESCAPE '\';

-- Step 2b: fall back to an Interactive Grid column alias
SELECT COLUMN_ALIAS INTO V_COL_ALIAS FROM APEX_APPLICATION_PAGE_RPT_COLS
WHERE APPLICATION_ID = V_APP_ID AND PAGE_ID = V_PAGE_ID
AND UPPER(COLUMN_ALIAS) = UPPER(V_COLUMN_NAME);
```

Works for any constraint on any page without a lookup table to maintain —
`UQ_AGR_PLANT_CODE` resolves to column `PLANT_CODE`, which then matches
`P40_PLANT_CODE` on whichever page fired the error.

```sql
/
```

Both rows sync to APEX automatically (app 101 is explicit, so `SYNC_TO_APEX`'s
guard clause passes).

### 8b. Read a label at runtime (PL/SQL page process)

```sql
:P21_BUTTON_LABEL := APP_TRANSLATE_PKG.GET_TRANSLATE_MESSAGE(
    p_code => 'BTN_FORWARD_INSPECTION', p_lang => V('G_LANG'), p_app_id => 101);
```

### 8c. Parameterised message with placeholders

```sql
-- Seed once:
APP_TRANSLATE_PKG.ADD_TRANSLATE_MESSAGE('MSG_QTY_EXCEEDS_LIMIT','EN',

-- Use at runtime:
v_msg := APP_TRANSLATE_PKG.GET_FORMAT_MESSAGE(
             p_code => 'MSG_QTY_EXCEEDS_LIMIT', p_lang => 'EN',
             p_param1 => TO_CHAR(45), p_param2 => TO_CHAR(30));

```

### 8d. Register the error handler on an application

APEX Builder → App *(e.g. 101)* → Edit Application Definition →
**Error Handling** → *Error Handling Function*:

```
APP_TRANSLATE_PKG.AGR_ERROR_HANDLER
```

Repeat for every AGR app (101–108).

### 8e. New table deployed — constraint messages appear automatically

```sql
-- Developer runs a migration:
ALTER TABLE AGR_EQUIPMENT ADD CONSTRAINT UQ_AGR_EQUIP_CODE UNIQUE (EQUIPMENT_CODE);
-- TRG_SEED_CONSTRAINT_MSG fires immediately, seeding:
--   EN: '[UNTRANSLATED] Constraint: UQ_AGR_EQUIP_CODE'
--   AR: '[غير مترجم] قيد: UQ_AGR_EQUIP_CODE'
```

Translator later opens the constraint-messages admin page (sourced from
`VW_AGR_CONSTRAINT_MESSAGES`, filtered to `TRANSLATION_STATUS = 'PENDING'`)
and replaces both with real text via `ADD_TRANSLATE_MESSAGE`. The very next
time that constraint fires, `F_CONSTRAINT_MSG` returns the real text — no
code deployment needed.

### 8f. Environment restore / bulk catch-up

```sql
-- After restoring a schema export where the DDL trigger didn't exist yet:
DECLARE v_s NUMBER; v_k NUMBER;
BEGIN
  APP_TRANSLATE_PKG.PRC_SEED_CONSTRAINT_MESSAGES(
      P_TABLE_PREFIX => 'AGR_%', P_SEEDED_COUNT => v_s, P_SKIPPED_COUNT => v_k);
END;
/

-- Then push everything to APEX for a specific app:
BEGIN
  APP_TRANSLATE_PKG.SYNC_ALL_TO_APEX(p_app_id => 101);
END;
/
```

## 9. Known Issues & Design Notes Summary

| # | Item | Detail |
|---|---|---|
| 1 | `UQ_TRANSLATE_KEY (CODE, LANG)` | Per-app/per-page override tiers in `GET_TRANSLATE_MESSAGE` cannot currently be exercised — only one row can exist per code/lang system-wide |
| 2 | `FORMAT_MESSAGE` params 6–8 | `%5`/`%6`/`%7` all substitute `p_param5` due to a copy-paste bug in the three highest-numbered branches |
| 3 | Double sync on every write | `ADD_TRANSLATE_MESSAGE` calls `SYNC_TO_APEX` directly *and* the compound trigger queues the same row — harmless (idempotent) but redundant work per statement |
| 4 | `SYNC_TO_APEX` requires explicit `APP_ID` | Rows inserted with `p_app_id => NULL` (global scope) are never pushed to APEX; pass a real app ID if the string needs to reach `apex_lang.message()` |
| 5 | `F_CONSTRAINT_MSG` never passes `P_APP_ID` | Constraint messages always resolve/seed at the shared (`APP_ID IS NULL`) tier, consistent with both seeding mechanisms in §6 |
| 6 | `G_LANG` vs `FSP_LANGUAGE_PREFERENCE` | Language detection in the error handler depends on the custom `G_LANG` application item being set correctly elsewhere in the session bootstrap — confirm it's populated before relying on Arabic error messages |
